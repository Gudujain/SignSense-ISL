# SignSense current architecture (Phase 0 baseline)

This document describes the checked-out implementation, not an intended or validated future design. The app was reachable at `http://127.0.0.1:5000/` during this inspection. No application or database behavior was changed.

## Browser screens and rendering

`GET /` serves `src/static/index.html`; the `screen-view` sections are switched in place by `SignSenseApp.switchScreen()` in `src/static/js/app.js`. `src/static/index.html` is the only HTML page. It contains onboarding (`#screenOnboarding`) and the six main screens:

| Screen | Main element | Content source |
|---|---|---|
| Home | `#screenDashboard` | `/api/learner/progress`, `/api/recommendations`; recent signs, stats, revision queue, quick actions. |
| Curriculum | `#screenCurriculum` | `/api/curriculum`; stage and sign cards, search and filters. |
| Practice | `#screenPractice` | Selected curriculum sign, browser camera stream and `/api/recognize`; attempt controls call `/api/assess`. |
| Recommendations | `#screenRecommendations` | `/api/recommendations`; rule-labelled cards with reference thumbnail, explanation, Practise and Dismiss. |
| History | `#screenHistory` | `/api/learner/progress` supplies recent attempts; rendered as a table with prediction candidate, assessment, explanation, latency and review action. |
| Settings | `#screenSettings` | Learner profile API plus browser-local appearance/camera preferences and history clear action. |

There are also a reference-detail `<dialog>` and developer diagnostics panel. These are overlays, not separate routes.

### Recommendations page, as seen during inspection

At inspection time the page showed two cards: **“Retry suggested — Explore sign 1”** with the explanation that the latest attempt could not be assessed, and **“A place to start — Explore sign 2”** with the explanation that it is the next prototype curriculum reference. Each card had a small reference image, a **Practise** button, and a **Dismiss** button. These were generated by `UNCERTAIN_RECOVERY` and `CURRICULUM_PROGRESSION` recommendations, respectively, from the database state present during inspection. The list can differ as learner history/dismissals change; when empty, the page says there are no active recommendations and directs learners to browse or return after practice.

## Flask routes

Routes in `src/server/app.py`:

| Method and path | Handler | Purpose |
|---|---|---|
| `GET /` | `index()` | Serves the single-page HTML. |
| `GET /api/curriculum` | `get_curriculum()` | Summary, stages and all signs. |
| `GET /api/curriculum/<sign_id>` | `get_curriculum_sign(sign_id)` | One sign or 404. |
| `GET /api/learner/profile` | `get_profile()` | Saved learner goal, level and research-consent flag. |
| `POST /api/learner/profile` | `update_profile()` | Persists profile preferences. |
| `GET /api/learner/progress` | `get_progress()` | Progress summary and recent attempts (used by History). |
| `GET /api/recommendations` | `get_recommendations()` | Ranked history-based recommendation list and request latency. |
| `POST /api/recommendations/dismiss` | `dismiss_recommendation()` | Stores a dismissed sign recommendation. |
| `POST /api/recognize` | `recognize()` | Decodes/infer on one frame, records diagnostics, adds candidate to server stability buffer, and optionally compares result with target after inference. |
| `POST /api/recognize/reset_stability` | `reset_stability()` | Clears server prediction stabilizer. |
| `POST /api/assess` | `assess()` | Assesses submitted attempt observations, updates learner state, returns fresh recommendations. |
| `GET /api/diagnostics` | `get_diagnostics()` | Runtime diagnostic counters/timings. |
| `POST /api/history/clear` | `clear_history()` | Clears attempts, progress and dismissed recommendations; keeps profile. |

Static assets are served by Flask at `/static/...` via `Flask(static_folder="../static", static_url_path="/static")`.

## Data schema observed in `signsense.db`

Schema is created/migrated by `StorageManager._init_db()` in `src/engine/storage.py`. This inspection queried `PRAGMA table_info` and row counts without changing data. Tables:

| Table | Fields and role |
|---|---|
| `learner_profile` | `id` primary key; `goal`, `skill_level`, `research_consent`, `created_at`, `updated_at`. One row was present at inspection. |
| `sign_progress` | `sign_id` primary key, `label`, attempt/correct/incorrect/uncertain counts, success/failure streaks, `mastery_score`, last-practice time, review interval and next-review time. One row was present. |
| `practice_attempts` | Autoincrement `id`, `sign_id`, `label`, model prediction/confidence/status, learner confirmation, correctness/uncertainty/discrepancy flags, feedback, serialized `assessment_json`, raw score/type, latency, timestamp. One row was present. Older databases receive three added evidence columns in `_init_db()`. |
| `dismissed_recommendations` | `sign_id` primary key and dismissal timestamp. Empty at inspection. |
| `sqlite_sequence` | SQLite-maintained autoincrement metadata. |

`StorageManager.record_attempt()` persists the attempt summary and assessment JSON. `get_recent_attempts()` decodes `assessment_json`; the browser History screen uses `learner_manager.get_progress_summary()` via `/api/learner/progress`. Progress and attempt data are updated from `/api/assess` through `LearnerModelManager.update_with_attempt()`.

## ML and reference model files

| File | Current role |
|---|---|
| `src/static/references/{1..9,A..Z}.jpg` | One curriculum/reference image per displayed label. `RecognitionEngine._load_reference_profiles()` reads these to build active template features and, if available, landmark profiles. |
| `models/hand_landmarker.task` | MediaPipe Tasks hand detector model loaded by `HandPoseAnalyzer`; configured with `num_hands=2`. |
| `svm_model.sav`, `mini_kmeans_model.sav` | Legacy root-level artifacts. The current Flask `RecognitionEngine` does not load these. |
| `ml_models/landmark_svc_letters_experimental.joblib` | Experimental candidate model artifact. The current Flask route/engine does not load it. |
| `src/ml/landmark_svc.py` | Feature-vector and SVC scoring helpers used by experiments, not wired into production web recognition. |

The active recognizer is a heuristic/template candidate generator, not a verified recognizer. When MediaPipe is available, it detects up to two hands but prediction uses the primary hand: hand landmarks are compared with reference landmark profiles and numeral finger-count rules may override the candidate. With MediaPipe unavailable, it falls back to color/edge/Hu-moment descriptors compared with one reference image per class. It returns an unvalidated template score (or no score), not a calibrated probability. The target is not passed to raw prediction by the API; target comparison is formed after candidate generation.

## Camera-to-result flow

```mermaid
sequenceDiagram
  actor Learner
  participant UI as Browser: app.js / video + canvas
  participant API as Flask: /api/recognize
  participant Rec as RecognitionEngine
  participant Pose as HandPoseAnalyzer / MediaPipe
  participant Assess as assessment.py + learner_model.py
  participant DB as SQLite: signsense.db
  participant Recs as recommender.py

  Learner->>UI: Enable camera / Start Attempt
  UI->>UI: getUserMedia; mirror and draw frame at 256x192 JPEG, quality 0.65
  loop While camera is active, about every 180 ms (one request at a time)
    UI->>API: POST base64 frame (no target)
    API->>Rec: recognize_base64_frame(frame)
    Rec->>Pose: analyze_frame(decoded BGR frame), if detector available
    Pose-->>Rec: up to two hand landmarks and derived features, or no hand
    Rec-->>API: candidate/status/raw uncalibrated score/diagnostics
    API-->>UI: raw prediction + optional post-prediction target comparison + stability
    UI->>UI: show status; while ATTEMPT_ACTIVE, append observation
  end
  Learner->>UI: Submit Attempt (explicit button)
  UI->>API: POST /api/assess with attempt UUID, target, observations, last prediction
  API->>Assess: assess_attempt(...)
  Assess->>DB: persist attempt and update sign progress through learner manager
  Assess->>Recs: request fresh recommendations
  API-->>UI: assessment, progress update and recommendations
  Learner->>UI: Cancel instead of submission
  UI->>UI: discard browser observations; reset server stability; do not call /api/assess
```

`SignSenseApp.startCamera()` in `src/static/js/app.js` obtains the browser video stream and starts the loop. `startInferenceLoop()` throttles recognition requests to approximately one every 180 ms. `captureAndRecognizeFrame()` draws a mirrored frame into a 256x192 offscreen canvas and posts a JPEG data URL. Selected frames are sent to the local Flask server; `src/static/index.html` privacy copy correctly says they are not stored in attempt history.

## Explicit attempt lifecycle

Lifecycle is in `src/static/js/app.js`, bound to buttons in `src/static/index.html`:

1. **Start Attempt** → `startAttempt()` ensures camera is active, creates `currentAttemptUuid`, stores current target, clears observation/prediction buffers, and calls `setAttemptState('ATTEMPT_ACTIVE')`.
2. **During attempt** → `updateRecognitionUI()` / `recordAttemptObservation()` append candidate, status, raw score/type, landmark/finger diagnostics, hand count and error fields. It does not grade continuously. Every ~180ms frame can add an observation.
3. **Submit Attempt** → `finishAttempt()` moves to `ASSESSING` and posts the collected observations plus target and UUID to `/api/assess`. `assess_attempt()` returns an ungraded/uncertain/not-assessed outcome under current validation constraints; the UI renders the returned state in `displayAssessmentResult()` and enters `FEEDBACK_READY`.
4. **Cancel** → `cancelAttempt()` clears observations and UUID and calls `resetToPreparation()`, which resets UI and requests `/api/recognize/reset_stability`. It does not submit an attempt.
5. **Retry / next sign** → feedback buttons reset to preparation, review reference, or choose the next curriculum sign.

The submit action is currently a mouse/touch button. There is no hands-free finish mechanism in this lifecycle.

## Evidence limits

This document traces code and inspects the live page, database schema, and model artifact names. It does not establish camera reliability, recognition accuracy, accessibility conformance, or sign-label correctness. The experimental SVC is not proof of production recognition; no independent learner/participant test is described here. UI issues in [the heuristic evaluation](hci/00-baseline.md) that came from the request are identified as reported observations, rather than silently presented as newly verified measurements.
